# 계보 그래프 진단 리포트 — 무엇이, 왜, 얼마나 안 읽히는가

작성: 데이터 분석가 · QA 역할. 목적은 새 전체화면 그래프 뷰어를 설계하기 *전에*
현재 렌더러(`js/wiki/graph.js`, 150편 시절 설계)가 446편 규모에서 구체적으로
어디서 깨지는지 숫자로 못박는 것. 이 문서는 렌더러나 데이터 파일을 고치지
않는다 — 진단 전용.

측정 환경: `python3 -m http.server 8899`, Chrome(자동화), 뷰포트 실측은
1280×700(표준 노트북 한 화면 가정)과 실제 브라우저 창(2752×1030, 3440×1030 —
둘 다 위 표준보다 훨씬 넓은 대형 모니터였다는 점을 감안해서 읽을 것) 두 기준을
같이 썼다.

**중요한 정정 하나**: 브리핑에는 "740개 간선"이라고 돼 있었지만, 실측
결과 `content/fields.js`의 `WIKI.INDEX`(→`WIKI.META`)를 실제로 로드해 센
계보 간선(parents 참조)은 **797개**다(댕글링 참조 0개, 중복 0개 — `WIKI.META`
446개 논문 전수 검사). 이하 모든 수치는 797개 기준.

## 1. 데이터 구조 분석

방법: `content/fields.js`를 Node로 실행해 `WIKI.META`(446개 레코드: slug, year,
title, ko, field, track, parents[])를 그대로 덤프한 뒤 Python으로 집계했다.
레이아웃 수치(SVG px 크기 등)는 `js/wiki/graph.js`의 `W.graph` 알고리즘을
Python으로 1:1 재현해 계산했고, 브라우저에서 실제 `WIKI.graph(WIKI.META, ...)`를
호출해 얻은 실측값(3138×5986px)과 **정확히 일치**함을 확인했다 — 이후 순수
Python 계산도 신뢰할 수 있다는 근거.

이 70개 긴 간선은 그래프의 왼쪽 끝(기초 레인, backprop/LSTM 위치)에서

레인 배경을 무시하고 그리므로(엣지는 레인과 무관하게 절대좌표로 그림)
**중간에 있는 다른 레인들의 배경 위를 가로질러 지나간다** — "이 선이 어느
레인 소속인지"가 시각적으로 사라진다.

### 1.5 교차 간선 수 추정

방법: `W.graph`가 실제로 그리는 시작점/끝점 좌표(베지어의 양 끝점, 곡선 자체는
직선으로 근사)를 기준으로 모든 간선 쌍(797×796/2 ≈ 31.7만 쌍)에 대해 선분
교차 여부를 계산했다(끝점을 공유하는 쌍은 "교차"로 세지 않음 — 정상적인 분기).

**결과: 약 14,587건의 교차.** (직선 근사이므로 실제 베지어 곡선 기준으로는
이 값에서 ±수천 정도 오차가 있을 수 있다 — "정확한 값"이 아니라 "이 정도
규모"로 읽을 것.) 간선 797개로 나누면 **간선 하나당 평균 18.3번 교차** —
어떤 간선을 하나 눈으로 따라가려 해도 18번 넘게 다른 선과 겹치는 지점을
지나간다는 뜻이다.

추가로 "간선이 무관한 노드 박스 위를 지나가는" 경우를 직선 샘플링으로
추정하면 **약 2,212건**(예: backprop→adam 간선이 imagenet·dropout-2012·
straight-through·dropout 박스 위를 지나감; resnet→efficientnet 간선이
yolo·densenet·focal-loss·mixup 박스 위를 지나감). 이건 "글자가 안 읽히는
곳"의 직접적 원인이다 — 노드 텍스트 위로 회색 선이 겹쳐 지나간다.

노드 박스 자기들끼리의 겹침(bbox overlap)은 **0건**이다 — `W.graph`의
레인 내 행 배치 로직(`while(rows[r]!==undefined && rows[r] > x-8) r++`)이
같은 레인 안에서는 겹치지 않게 잘 밀어내고 있다. **즉 "박스가 박스를
가리는" 문제는 없고, "선이 박스와 다른 선을 가리는" 문제가 압도적이다** —
이건 새 뷰어 설계에서 중요한 구분이다(노드 재배치보다 엣지 라우팅이
핵심 병목).

### 1.6 최장 경로와 깊이 분포

DAG 위상정렬 성공(사이클 없음 확인, 446/446 정렬됨). **최장 경로 = 17개
간선, 18개 노드(depth 0~17)**:

```
퍼셉트론(1958) → 역전파(1986) → LeNet-5(1998) → AlexNet(2012) → 드롭아웃(2014)
→ 배치정규화(2015) → 레이어정규화(2016) → Transformer(2017) → GPT-1(2018)
→ GPT-2(2019) → 스케일링법칙(2020) → GPT-3(2020) → Chinchilla(2022)
→ LLaMA(2023) → Mistral 7B(2023) → Mixtral 8x7B(2024) → DeepSeek-V3(2024)
→ DeepSeek-R1(2025)
```

깊이 분포(0=원천 노드)는 완만한 종형이 아니라 **8~15단계 구간에 27~43개씩
고르게 몰려 있다**(depth 8: 42, 10: 43, 12: 40, 14: 34개 등) — 계보가
"몇 세대 안 되는 얕은 나무"가 아니라 **18세대 깊이의 진짜 긴 사슬**이라는
뜻이고, 이는 "부모 위·자식 아래 1~2홉만 보여주는" 로컬 그래프 설계가
타당한 이유이기도 하다(전체를 한 트리로 펼치면 세로로 18단 이상 나온다).

### 1.7 연결 성분

**연결 성분 2개**: 거대 성분 444편 + 고립 쌍 1개(**HNSW(2016) → FAISS(2017)**,
이 둘은 나머지 444편과 계보상 전혀 연결돼 있지 않다). 완전히 고립된
단일 노드(부모도 자식도 없는 논문)는 **0개** — 모든 논문이 최소 하나의
계보 관계는 갖고 있다.

## 2. 현재 렌더링 실측 (브라우저)

`python3 -m http.server 8899`로 실제 `index.html`을 띄우고 Chrome
자동화로 측정했다.

### 2.1 홈 하단 전체 계보 그래프

- **SVG 크기: 3138 × 5986px** (Python 재현 계산과 브라우저 실측이 정확히
  일치 — `svg.getAttribute('width'/'height')`로 확인).
- DOM: `g.node` 446개, `path.edge` 797개, `<svg>` 내부 총 엘리먼트 **3,114개**.
- 렌더 시간은 **문제가 아니다** — `WIKI.graph(WIKI.META, WIKI.FIELDS, ...)`를
  직접 호출해 문자열 생성 0.80ms, `innerHTML` 삽입(DOM 파싱) 4.70ms, 합쳐서
  **5.5ms 미만**. HTML 문자열 자체는 273KB. 즉 이 그래프는 "느려서" 못 읽는
  게 아니라 순수하게 밀도 문제다.
- **컨테이너(`#gbox`, `.graph-viewport`) 실제 화면 크기는 1442×737px인데
  내용은 3138×5995px** — 가로 2.2배, 세로 8.1배를 스크롤해야 전체를 볼 수
  있다. 확대/축소 버튼(100%/+/−)이 있지만 축소해도 결국 "3138×5986px 분량의
  정보"라는 총량은 줄지 않으므로, 축소하면 글자가 안 보이고 100%로 두면
  스크롤이 끝없다 — 딜레마.
- 노드 박스끼리의 겹침은 0건(1.5절과 동일 계산, 레이아웃이 레인 내에서는
  겹치지 않게 밀어냄). 문제는 **선이 배경 전체를 뒤덮는 것**과 **한 화면에
  다 안 들어오는 것** 둘이다.
- 스크린샷으로 확인한 구체적 장면: 그래프 최상단(기초·학습 알고리즘 레인)의
  "역전파" 노드에서 가느다란 선 수십 개가 부채꼴로 퍼져 나가 오른쪽 끝(2020년대
  영역)까지, 그리고 아래쪽의 컴퓨터비전·언어표현 레인 배경 위까지 가로질러
  뻗어 있다 — 1.4절에서 계산한 "역전파발 30년 이상 간선 다수"가 그대로
  시각적 "빗자루살" 패턴으로 나타난다.
- LLM 레인으로 스크롤하면(GPT-3 근방) 2018~2023년 칸마다 5~7개 박스가
  세로로 빽빽하게 쌓여 있고, "decoder-only Tr…", "Universal Trans…",
  "1 epoch 만으로 충분하다"(이건 15자 이하라 안 잘림) 등 **제목 2행("연도 ·
  제목")은 육안으로도 거의 전부 "…"로 잘려 있다.**

### 2.2 분야 페이지 그래프 (`#/f/llm`)

- SVG 1434×1596px, 노드 66개, 간선 95개. 트랙 레인 6개(아키텍처 원점,

- 이번 자동화 환경(초대형 모니터, 뷰포트 폭 3400px대)에서는 컨테이너가
  SVG보다 넓어 스크롤 없이 다 보였지만, **표준 노트북 화면(1280×700 가정)
  기준으로 재계산하면 이 그래프는 화면의 39.1%만 들어온다**(1.4절 실험,

  "Universal Trans…", "PaLM 2 Technical R…" 등 — track 레인 안에서도 여러
  줄이 겹쳐 쌓이고 Transformer 노드에서 나온 선들이 아래쪽 레인들을
  가로지른다(홈 그래프와 같은 패턴, 규모만 작음).
- 참고(재현성 메모): 해시 라우팅 직후(전체 리로드 없이) 첫 스크린샷 1회에서
  CSS가 전혀 적용되지 않은 상태(기본 브라우저 스타일의 사이트맵 목록)가
  잠깐 찍힌 적이 있었는데, 페이지를 새로고침하니 재현되지 않았다 — 이
  세션의 자동화 도구 쪽 타이밍 문제일 가능성이 높아 **확정 버그로 보고하지
  않는다**(못 잰 것으로 남겨둠). 실제 사용자 트래픽에서 이런 현상이
  보고되면 별도로 재현 확인이 필요하다.

### 2.3 논문 페이지 로컬 그래프 (`#/p/transformer`)

- `WIKI.localGraph('transformer')`를 직접 호출한 실측: **`truncated: true`**,
  노드 52개(중심 1 + 부모 3 + 자식 48), SVG 1060×736px, HTML 26.9KB.
  생성 자체는 0.80ms로 빠르다.
- **중요한 설계 허점을 실측으로 확인했다**: `js/wiki/graph.js`의 truncation
  로직(`total>20`이면 `p2=c2=[]`로 만들어 2홉을 버림)은 **1홉(직계 자식)
  개수는 전혀 제한하지 않는다.** transformer처럼 자식이 48편인 허브는
  2홉을 다 잘라내도 "1(중심)+3(부모)+48(자식) = 52개 노드"가 그대로
  남아 truncation의 의도(20개 이하로 억제)를 완전히 벗어난다. 코드 주석
  자체가 이미 이 사실을 알고 있다("한 줄에 너무 많으면 접어서 여러 줄로 —
  안 그러면 SVG 폭이 3000px를 넘어 … transformer는 자식이 20편")고 적어
  뒀는데, 실측 결과 지금은 20편이 아니라 **48편**이다 — 데이터가 늘면서
  이 안전장치 자체가 낡아버린 사례.
- 폴딩 로직(`PERROW=7`)이 48개를 7개씩 여러 줄로 접어 SVG 폭 자체는
  1060px로 억제하지만, 그 대가로 **세로 길이가 늘어나고(736px, 자식만
  7줄)**, 로컬 그래프인데도 "1~2홉 요약"이라는 원래 목적과 달리 한 화면에
  거의 50개 박스가 쏟아지는 현상은 그대로다.
- 이 특정 화면의 스크린샷은 이번 세션에서 안정적으로 캡처하지 못했다
  (`Page.captureScreenshot`가 반복적으로 30초 타임아웃 — 브라우저 자동화
  도구 쪽 문제로 보이며, 같은 세션에서 다른 무거운 SVG는 정상 캡처됐다).
  **이 부분은 "못 쟀다"로 명시한다** — DOM 수치(52노드, truncated=true,
  1060×736px)는 신뢰할 수 있지만 육안 스크린샷 증거는 없다.

## 3. 문제 목록 (우선순위 순, 근거 수치 포함)

1. **한 화면에 절대 안 들어오는 절대량.** 홈 그래프는 3138×5986px인데
   표준 뷰포트(1280×700)엔 그 4.8%만 들어온다. 스크롤이 "가끔 필요한 것"이
   아니라 "항상 필요한 것"이다 — §4 실험에서 노드 15개(전체의 3%)만
   있어도 이미 81.2%로 한 화면을 못 채운다.
2. **허브 노드의 극단적 진출차수(멱법칙).** Transformer(48)·GPT-3(46)·
   BERT(36)·backprop(31)·LSTM(26)·ResNet(24) 6개 노드가 전체 간선 797개
   중 211개(26.5%)를 만들어낸다. 로컬 그래프에서 이 truncation 안전장치를
   무력화하고(52노드 렌더), 전체 그래프에서는 부채꼴 "빗자루" 패턴으로
   시각적 소음의 핵심이 된다.
3. **긴 간선이 레인 경계를 무시하고 화면을 대각선으로 가로지른다.** 70개
   (8.8%)가 10년 이상 간선이고, 그중 63개가 backprop·LSTM 단 둘에서
   나온다. 엣지가 레인 배경과 무관하게 그려져 "이 선이 어디 소속인지"가
   사라진다.
4. **교차선이 압도적으로 많다.** 추정 14,587건, 간선당 평균 18.3회 교차.
   이 자체가 "스파게티"로 보이는 직접 원인이며, 그중 약 2,212건은 무관한
   노드 박스 위를 지나가 텍스트를 가린다(예: resnet→efficientnet 선이
   yolo·densenet·mixup 박스를 관통).
5. **분야×연도 특정 칸의 극단적 밀집.** LLM×2022 한 칸에 15편이 몰려
   레인 하나가 740px 높이로 부풀고, 최근 5년(2020–2024)에 전체의 55.4%
   (247편)가 몰려 있어 그래프 오른쪽 절반이 왼쪽 절반보다 압도적으로
   빽빽하다.
6. **라벨이 사실상 항상 잘린다.** `clip(m.ko,16)`으로 16자를 넘는 한국어
   라벨 29개(6.5%)가 잘리지만, 더 심각한 건 부제(연도·원제) 줄 —
   `clip(m.title,18)` 기준 **446편 중 436편(97.8%)의 영문 원제가 18자를
   넘어 거의 항상 "…"로 잘린다.** 로컬 그래프는 한국어 라벨 클립이
   15자라 36개(8.1%)가 잘린다.
7. **로컬 그래프의 truncation 안전장치가 허브 앞에서 무력화된다.**
   `total>20`이면 2홉만 버리고 1홉은 그대로 두는 로직이라, 자식 48편인
   transformer 같은 허브는 "요약"이 아니라 "1~2홉 다 펼친 전체 그래프의
   축소판"이 된다(52노드).
8. **깊이 18세대짜리 진짜 긴 사슬.** 최장 경로 17간선/18노드
   (퍼셉트론→…→DeepSeek-R1). 계보를 한 트리로 완전히 펼치는 시도 자체가
   무리라는 근거 — 부분(로컬) 뷰가 구조적으로 필요하다.
9. **경미**: 연결 성분 2개(444+2, HNSW·FAISS 고립 쌍) — 전체 지도에
   이 둘을 넣으면 나머지 444편과 아무 관계도 없는 섬 하나가 따로 뜬다.

## 4. 설계 제약 도출 (실험 기반)

**실험 방법**: `design/mock/graph-density-test.html` — 실제 `js/wiki/core.js`
+ `js/wiki/graph.js` + `content/fields.js`를 그대로 로드해(로직 사본 아님)
`WIKI.META`에서 앞 N편(N=15/30/60/120/250/446)을 뽑아 `WIKI.graph()`로
그리고, 1280×700 고정 뷰포트에 전체 SVG의 몇 %가 들어오는지 측정. 추가로
실제 분야별 그래프(llm/vision/nlp/foundations/efficiency)도 같은 기준으로
쟀다.

| N (또는 분야) | SVG 크기 | 1280×700에 들어오는 비율 |
|---|---|--:|
| 15편 | 1576×398 | 81.2% |
| 30편 | 2144×598 | 59.7% |
| 60편 | 2712×814 | 40.6% |
| 120편 | 2854×1844 | 17.0% |
| 250편 | 2996×4436 | 6.7% |
| 446편(전체) | 3138×5986 | 4.8% |
| nlp 분야(16편) | 1292×332 | **99.1%** |
| foundations 분야(13편) | 1434×348 | 89.3% |
| efficiency 분야(35편) | 1434×780 | 80.1% |
| vision 분야(42편) | 2002×946 | 47.3% |
| llm 분야(66편) | 1434×1596 | 39.1% |

**결론**: 현재의 고정 박스 크기(126×40px)와 고정 연도 간격(142px)을 그대로
쓰는 한, **표준 노트북 화면 하나(1280×700)에 스크롤 없이 다 들어가는
한계는 대략 논문 15~20편, 그리고 그 15~20편이 다루는 연도 범위가 좁아야
한다는 전제까지 붙는다**(연도 범위가 넓으면 15편이어도 81%에 그친다 —
1.4절의 backprop 같은 장기 스팬 허브가 하나만 섞여도 폭이 확 늘어난다).
16~35편짜리 개별 분야조차 80~99% 사이를 오가며 딱 걸치는 수준이고, 66편
(llm 분야 하나)부터는 39%로 확실히 못 들어간다. 지금 전체 그래프는 446편,
즉 이 한계의 **20~30배** 규모다.

새 전체화면 뷰어가 반드시 감당해야 할 것:

1. **"한 화면에 다 보여준다"는 목표 자체를 버려야 한다.** 실험상 15~20개가
   상한이고 446개는 그 30배 — 확대·압축·범례 개선 정도로 좁혀질 격차가
   아니다. 초기 진입 화면은 처음부터 **부분집합**(분야 하나, 또는 시대
   구간 하나, 또는 특정 논문 중심 로컬 뷰)이어야 하고, "전체"는 명시적으로
   축소한 개요(미니맵류) 형태로만 존재해야 한다.
2. **허브 노드(자식 ≥10) 전용 처리가 필요하다.** 6개 허브가 간선의
   26.5%를 만든다 — 이 소수를 어떻게 그리느냐가 전체 가독성을 좌우한다.
   지금처럼 "모든 자식을 다 그린다"는 규칙 하나로는 transformer(48)에서
   무조건 깨진다. 허브는 자식을 접어서 보여주거나("+34개 더 보기"),
   개수 자체를 요약 배지로만 보여주고 펼침은 사용자 행동으로 미뤄야 한다.
   로컬 그래프의 `total>20` truncation도 **1홉 개수 자체에 상한을 둬야**
   지금처럼 허브 앞에서 무력화되지 않는다.
3. **긴 간선(10년 이상, 70개)을 레인 경계를 존중하는 방식으로 다시
   그려야 한다.** 직선/베지어로 화면을 대각선 관통시키는 대신, 나머지
   자식들과 마찬가지로 방향성은 유지하되 예컨대 "선택 시에만 강조"(이미
   `GRAPH-INTERACTION.md`가 정한 dim 규칙)처럼 기본 상태에서는 더 강하게
   억제하는 처리가 필요하다 — 지금 dim은 "선택 안 했을 때"만 적용되므로,
   장거리 간선은 선택 여부와 무관하게 기본값 자체를 옅게 가는 것을
   검토해야 한다.
4. **엣지 라우팅이 노드 재배치보다 시급하다.** 노드 박스끼리는 겹치지
   않는다(0건 실측) — 문제는 선이 선·박스와 겹치는 것(교차 ~14,587건,
   박스 관통 ~2,212건)이다. 새 뷰어는 레인 내부 노드 위치를 지금보다
   더 손볼 필요는 적고, **엣지가 어떻게 그려지는지**에 예산을 써야 한다.
5. **라벨 잘림은 박스 크기가 아니라 정보 위계 문제로 풀어야 한다.**
   원제(title) 97.8%가 잘리는 것은 "글자를 더 작게/박스를 더 크게"로
   해결되는 수준이 아니다(그러면 밀도 문제가 더 악화된다) — 원제 전체는
   호버/선택 카드 같은 2차 표시로 옮기고, 노드 자체에는 애초에 안 잘리는
   짧은 정보(한국어 약칭·연도)만 남기는 편이 낫다.
6. **최소 18세대 깊이를 감당할 수 있는 부분 뷰가 기본이어야 한다.**
   전체를 한 트리로 펼치면 세로 18단 이상 — 로컬 그래프(부모/자식 1~2홉)
   접근 자체는 유지하되, §3-7에서 지적한 허브 예외 처리를 반드시
   보강해야 한다.
7. **분야×연도 핫스팟(예: LLM×2022=15편)에 대한 별도 밀집 처리.** 연도
   축을 압축 등간격으로 배치하는 지금 방식은 "빈 연도 없앤다"에는
   맞지만 "한 칸에 15개 몰리는 문제"는 전혀 해결하지 못한다 — 밀집 연도
   칸 안에서 추가로 접거나(월/분기 세분화는 데이터에 없으므로 무의미),
   같은 칸 안 논문들을 서브그룹으로 묶는 등의 처리가 필요하다.

**못 잰 것 (명시)**:
- 실제 다양한 사용자 화면 크기(태블릿, 4K, 브라우저 확대 150% 등)에서의
  체감 가독성은 못 쟀다 — 1280×700 가정 하나로만 실험했다.
- 색맹 시뮬레이션, 실제 스크린리더 낭독 테스트는 안 했다(이 진단은
  시각 밀도 전용).
- `#/f/llm` 스크린샷 캡처 초반에 관찰된 "CSS 미적용" 1회성 현상은
  재현이 안 돼 원인 규명을 못 했다(§2.2 참고).
- 논문 페이지 로컬 그래프(`#/p/transformer`)의 실제 화면 스크린샷은
  자동화 도구의 반복적 캡처 타임아웃으로 못 얻었다 — DOM 수치만 확보.
- 베지어 곡선 자체 기준의 정확한 교차 횟수(직선 근사가 아닌)는 계산
  안 했다 — 규모감(약 1.4만 건)만 유효하다.
