# 접근성 · 성능 감사 — 책장 개편 전 기준선

이 문서는 개편(446편 책장) 착수 **전** 현재 상태를 실측한 기준선과, 개편이 지켜야 할 예산·요건이다.
측정은 `python3 -m http.server 8899`로 로컬 서빙 후 Chrome DevTools Performance API(`performance.getEntriesByType`, `performance.now()`)와
`stat`/Node/PIL을 사용한 실측치다. **추정치는 "추정"이라고 표시했고, 못 잰 항목은 명시했다.**

측정 환경 메모: 이 세션은 다른 에이전트와 Chrome 탭 그룹을 공유하고 있어 탭이 중간에 다른 세션에 의해
재사용되는 일이 있었다. 그 때문에 일부 warm-cache 수치가 섞여 있으며, 아래 각 표에 cold/warm 여부를 표기했다.

**중요:** `python3 -m http.server`는 gzip을 하지 않으므로 로컬 측정치(§1.2)는 gzip 없는 raw 전송량이다.
실제 정적 호스팅(GitHub Pages 등)이 gzip/br을 지원한다면 전송량은 표의 "gzip 시" 열에 가깝다. **이 프로젝트가 최종 어떤 정적 호스트에 올라가는지, 그 호스트가 압축을 제공하는지는 확인하지 못했다** — 배포 전 확인 필요.

**놓칠 뻔한 사실:** `content/meta.json`(178KB, gzip 66KB)은 브리프에 "신규"라고 적혀 있는데, 실제로는 **`js/wiki/*.js` 어디에서도 fetch되지 않는다** (`grep -rn "meta.json" js/` 결과 없음). 즉 저자 표기 기능은 아직 배선되지 않았고, 개편 시 이 178KB를 새로 얹어야 한다는 뜻이다. 홈 예산(§2)에 이 178KB를 반드시 포함해서 계산해야 한다.

### 2.2 446개 DOM 실험 (실측)

`design/mock/spine-446-test.html`을 만들어 책등 446개(요소당 4개 DOM 노드: 컨테이너 div + title span + year span + author span, `flex-wrap` 레이아웃, 가변 높이)를 실제로 렌더링하고 측정했다:

| 지표 | 값 |
|---|---:|
| DOM 노드 총합 | 1,792 (446×4 + 문서 골격) |
| `appendChild` (documentFragment 1회 삽입) 소요 시간 | **2.5 ms** |
| 강제 리플로우(`offsetHeight` 읽기) 소요 시간 | **0.1 ms** |

**결론: 446개를 한 번에 DOM에 넣는 것 자체(레이아웃/스크립트 비용)는 문제가 아니다.** flex/grid 레이아웃에서 446개 박스는 최신 브라우저에 전혀 부담이 안 된다. 문제는 노드 수가 아니라:
1. 각 책등에 표지 썸네일 `<img>`가 붙는 순간 (§3),
2. 각 책등이 접근성 트리에 올라가는 비용(포커스 가능 요소 446개 — 이건 키보드 사용자에게 실질적 부담, §4.5 참고),
3. 인라인 스타일/CSS 커스텀 프로퍼티를 446번 계산하는 비용(색상 `hsl()` 인라인 스타일을 쓴 이 테스트조차 2.5ms — 실 서비스에서 분야색을 CSS 클래스로 처리하면 더 빠를 것).

**권고: 가상 스크롤은 불필요하다.** DOM 446개는 쌀 정도로 싸다. 대신:
- 이미지 로딩만 지연시키면 된다(§3) — `content-visibility: auto`를 책등 컨테이너에 걸어 오프스크린 레이아웃/페인트 비용을 스킵하는 것으로 충분.
- 키보드 순회 446개는 별도 문제이므로 §4.5에서 완화책을 제시한다(로빙 tabindex 또는 섹션별 랜드마크 분할).

### 3.3 권고: `loading="lazy"` + `content-visibility: auto` 조합, IntersectionObserver는 불필요

비교:

| 전략 | 장점 | 단점 |
|---|---|---|
| `loading="lazy"` (네이티브) | 구현 0줄. 브라우저가 뷰포트 근접도 기반으로 알아서 스케줄링. 이미 논문 그림에서 쓰고 있음(`app.js:615`) — 패턴 일관성. | 뷰포트 판정 임계값을 세밀 제어할 수 없음(브라우저마다 다름). |
| `IntersectionObserver` 수동 구현 | 임계값/rootMargin 세밀 제어, 로드 우선순위 커스터마이즈 가능. | 코드 추가, 버그 표면 증가. 이 프로젝트는 "빌드 없음 vanilla JS" 제약이라 무거운 추가 로직을 피하는 게 브리프 정신에 맞음. |
| `decoding="async"` | 메인 스레드 디코딩 블로킹 방지. 추가 비용 없음. | 단독으로는 지연 로딩 효과 없음 — `loading="lazy"`와 병행 필수. |
| `content-visibility: auto` (컨테이너에) | 오프스크린 책등의 레이아웃·페인트·이미지 디코딩 자체를 스킵. `loading="lazy"`보다 상위 레벨에서 렌더링 비용을 아낌. | `contain-intrinsic-size`를 반드시 지정해야 함 — 안 하면 스크롤바가 튀는 문제(레이아웃 시프트) 발생. |

**권고: 세 가지를 함께 쓴다.**
```html
<div class="spine" style="content-visibility:auto; contain-intrinsic-size: <너비>px <높이>px">
  <img src="thumbs/<slug>.jpg" alt="<title> 표지" loading="lazy" decoding="async" width="<w>" height="<h>">
</div>
```
`IntersectionObserver`는 이 사이트 규모(446장, 순수 vanilla JS, 빌드 없음 제약)에서 얻는 이득 대비 코드/유지비가 안 맞는다 — 기각.

### 3.4 레이아웃 시프트(CLS) 방지

- `<img>`에 **명시적 `width`/`height` 속성**을 반드시 넣는다 (썸네일 생성 시 고정 비율로 만들면 됨, 예: 3:4). 브라우저가 종횡비를 미리 계산해 자리를 확보한다.
- `content-visibility: auto`를 쓰는 컨테이너는 `contain-intrinsic-size`로 예상 높이를 지정해야 스크롤 중 크기가 0→실제값으로 튀는 걸 막는다.
- 책 높이가 데이터(백링크 수)에 비례한다고 브리프에 나와 있으므로(§1 LIBRARY-BRIEF), **책등의 높이 자체는 이미지 로드 전에 데이터로 계산 가능** — 썸네일 로드 완료 여부와 무관하게 책등 레이아웃이 고정되도록, 표지 이미지는 책등이 아니라 "책 꺼내기(선택)" 상태에서만 로드되는 별도 레이어로 설계하는 게 가장 안전하다(홈에서는 책등만, 표지 이미지는 클릭 후 지연 로드).

### 4.3 카드/책등 링크 시맨틱 — `role="link"` + `data-go`, 실제 `<a href>` 아님

| 심각도 | 문제 | 위치 |
|---|---|---|
| **High** (책장 개편에서 그대로 답습하면 안 됨) | 분야 카드·검색 결과·계보 그래프 pill 등이 `<div class="card" tabindex="0" role="link" data-go="#/f/...">`로 구현되어 있고, 실제 `href`가 없다. 클릭은 전역 위임 리스너(`app.js:651`)가, 키보드는 전역 keydown 위임(`app.js:788-791`)이 Enter/Space를 가로채 `W.go()`를 호출하는 방식. 동작은 하지만: (1) 마우스 우클릭 "새 탭에서 열기"/가운데 클릭 불가, (2) 브라우저 상태바에 목적지 URL 미리보기 없음, (3) `role="link"`인데 Space로 활성화되는 건 표준과 어긋남(링크는 Enter만, Space는 버튼의 활성화 키) — 스크린리더가 "링크"라고 안내하지만 실제 동작은 버튼에 가까움. | `js/wiki/app.js:379` (분야 카드), `:457` (논문 카드), `:527`,`:553` (그래프 pill) |
| 참고 | 이미 `href="#/p/..."` 형태의 진짜 `<a>`도 혼재한다(`app.js:232` nav-tree 링크, `:328`,`:346`,`:358` 위젯 링크). 즉 두 패턴이 코드베이스에 공존 — 일관성 문제이기도 함. | `app.js:232,328,346,358` |

**책장 개편 함의:** 446개 책등은 반드시 진짜 `<a href="#/p/<slug>">`여야 한다. `role="link"`+`tabindex`+`data-go` 패턴을 새 책등에도 반복하면, 446개 규모에서 이 문제가 훨씬 크게 체감된다(마우스 오른쪽 클릭으로 여러 논문을 새 탭에 열어보는 게 서재 탐색의 자연스러운 사용 패턴인데 그게 막힘).

## 5. 책장 개편이 지켜야 할 접근성 요건 (체크리스트)

구현자가 아래 항목을 하나씩 자가 점검할 것. 괄호 안은 관련 근거 섹션.

**구조**
- [ ] 책등은 실제 `<a href="#/p/<slug>">`다. `role="link"`+`tabindex`+`data-go` div 패턴을 쓰지 않는다. (§4.3)
- [ ] 홈 페이지에도 `<nav>` 랜드마크가 있다(분야 내비게이션이든 책장 자체든). (§4.1)
- [ ] 책장 섹션(분야/그룹별 서가)마다 `<h2>`/`<h3>`로 의미 있는 헤딩 계층을 만든다 — 21개 분야를 평평한 `h3` 나열로 두지 않는다. (§4.1)
- [ ] 라우트 전환 시 `document.title`을 갱신한다(예: "Transformer — AI Wiki"). (§4.2)
- [ ] 라우트 전환 시 포커스를 `<main>`(또는 새 콘텐츠의 첫 헤딩)으로 옮기거나, 최소한 `aria-live` 영역으로 페이지 전환을 안내한다. (§4.2, §4.7)

**책등 콘텐츠**
- [ ] 책등의 스크린리더 텍스트는 "제목, 연도, 저자"가 실제 텍스트로 들어간다(`aria-label`로 뭉개지 않고, 진짜 텍스트 노드로 — 텍스트 확대/번역 확장 프로그램과도 호환). (LIBRARY-BRIEF §4)
- [ ] 저자 정보 없는 논문(`meta.json`에 없는 경우)도 책등 레이아웃이 깨지지 않고, 스크린리더가 "저자 정보 없음"을 침묵으로 넘기지(빈 `<span></span>` 남기지) 않는다 — 아예 노드를 생략한다.
- [ ] 연도·메타 텍스트 색은 `--text-faint`가 아니라 AA를 통과하는 토큰을 쓴다(§4.6에서 `--text-faint`가 양쪽 테마 모두 실패 확인됨 — 새 토큰 값 조정이 필요하면 `design/DESIGN-SYSTEM.md` 담당자와 협의).

**이미지(표지 썸네일)**
- [ ] 원본 `p-01.png`(평균 490KB, 최대 670KB)를 절대 그대로 쓰지 않는다 — 반드시 리사이즈 파이프라인을 거친다. (§3.1)
- [ ] `loading="lazy"` + `decoding="async"`를 모든 썸네일 `<img>`에 적용한다. (§3.3)
- [ ] 썸네일 컨테이너에 `content-visibility:auto` + `contain-intrinsic-size`를 적용해 오프스크린 비용을 없앤다. (§3.3)
- [ ] `<img width height>`를 명시해 레이아웃 시프트를 막는다 — 또는 책등 자체를 데이터 기반 크기로 먼저 확정하고 표지 이미지는 선택 시에만 로드한다. (§3.4)
- [ ] `alt`에 논문 제목이 들어간다(빈 `alt=""`로 두지 않는다 — 표지는 장식이 아니라 식별 정보다). 기존 논문 그림의 `alt=""` 패턴(§1.4)을 표지에는 반복하지 않는다.

**키보드/포커스**
- [ ] 446개 책등을 Tab만으로 순회하지 않아도 되는 경로를 제공한다 — 예: 분야 랜드마크 간 이동(`h2`/`h3`로 스크린리더 사용자가 헤딩 단위 이동 가능), 또는 검색으로 바로 점프. 이미 있는 `/` 검색 단축키를 책장에서도 강조.
- [ ] Escape로 어떤 패널을 닫든, 포커스가 항상 의미 있는 곳(연 버튼 등)으로 돌아간다 — blur만 하고 방치하지 않는다. (§4.7)
- [ ] 검색 결과 목록은 `role="option"` + `aria-selected` + input의 `aria-activedescendant`로 완전히 배선한다(책장 개편과 별개로 기존 버그이지만, 책장에서 검색 의존도가 커지므로 같이 고칠 것을 권장). (§4.4)
- [ ] 포커스 링이 명확한 대비로 보인다 — 특히 검색창(`outline:none` 제거 또는 강한 대체 표시 추가). (§4.5)

**모션/테마**
- [ ] 책 은유 관련 신규 애니메이션(있다면)도 `prefers-reduced-motion: reduce`를 존중한다(기존 `tokens.css:463`처럼). LIBRARY-BRIEF §2/§4가 이미 "방해되는 모션 금지"를 못박았으므로, 새 CSS도 같은 미디어쿼리 블록 안에 들어가야 한다.
