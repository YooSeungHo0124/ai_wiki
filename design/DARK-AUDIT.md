# 다크 테마 전수 감사 (DARK-AUDIT)

- 감사자: 별도 에이전트(제품 코드 미수정, 관찰만)
- 방법: `python3 -m http.server 8899`로 기동 → `localStorage.setItem('wiki-theme','dark')` 로 다크 전환 → Chrome(코드용 브라우저 자동화)로 홈/분야/논문/검색/`#/growing`/`#/course`/책장 커버 카드/좌측 내비/호버 미리보기/계보 그래프(임베드+전체화면)를 스크린샷 + `getComputedStyle`이 아니라 **`css/tokens.css`에 실제 정의된 `html[data-theme="dark"]` 값**(브라우저가 그대로 이 리터럴을 resolve하므로 소스값 = computed값)을 Python으로 WCAG 상대휘도 공식에 대입해 실측. 스크립트: `/data/tmp/.../scratchpad/contrast.py` (세션에만 존재, 재현 시 아래 값 그대로 재계산 가능).
- 좁은 화면은 `http://127.0.0.1:8901/mobile-frame.html`(390×844 iframe)로 홈/분야 페이지 확인.

## 총평

**다크 테마는 뒷생각(afterthought)이 아니다 — 토큰 설계는 실제로 잘 짜여 있다.** `css/tokens.css`는 라이트/다크를 프리미티브 단계부터 분리하고, 21개 분야색은 다크용 `-D` 값을 따로 갖고 있으며 주석에 실측 대비 수치까지 남겨뒀다. 실제로 이번 감사에서 21개 분야색 × 텍스트/배경 조합, 책등 밴드 잉크, 칩 on-상태, 상태색, 성장단계색을 전수 재계산한 결과 **거의 전부 AA를 넉넉히(5:1~10:1) 통과**한다 — "색을 다크용으로 새로 골랐다"는 코드 주석의 주장은 대체로 사실이었다.

문제는 색 토큰이 아니라 **세 군데의 구조적 빈틈**에서 나온다.

1. **`--text-faint` 토큰이 문서의 주장과 달리 `--surface`/`--surface-raised`/`--surface-sunken` 위에서 AA(4.5:1)에 실제로 미달**한다 — `--bg-page` 기준으로만 계산해 놓고 그 값을 다른 표면에도 재사용한 것으로 보인다. 이 토큰을 쓰는 4개 실제 컴포넌트(그래프 클릭 카드의 연도, 책등 하단 저자/연도, 계보 그래프 축 라벨) 중 다수가 실측 미달이다.
2. **"원문 PDF에서 잘라낸 흰 배경" 자산(figures, covers)에 다크 모드 처리가 전혀 없다.** 이건 21개 분야 색 재설계나 책장 개편과는 다른 팀(콘텐츠 파이프라인)이 만든 자산이라 이번 토큰화 작업의 손이 닿지 않은 것으로 보인다 — 논문 페이지의 "원문에서 가져온 그림" 절과, 책장에서 책 클릭 시 뜨는 호버 미리보기 카드 양쪽에서 매번 순백색 사각형이 그대로 튀어나온다. **446편 중 실제 커버 이미지가 있는 논문(= `covers/_missing.json`에 없는 대다수) 전부**가 영향권이다.
3. **테마 결정 로직이 `<head>`가 아니라 body 맨 끝의 `js/wiki/app.js`에 있어 FOUC(라이트→다크 깜빡임) 구조를 갖고 있다.** 실제로 매 로드마다 보이는지는 네트워크 속도에 달려 있지만, 코드 구조상 최소 한 프레임은 잘못된 테마로 페인트될 여지가 있다.

21개 분야 색 재설계, 책등 잉크 계산, 그래프 선택 강조색 같은 "여러 에이전트가 병렬로 만진" 부분들은 서로 잘 맞아떨어졌다. 반대로 **아무도 담당하지 않은 채 방치된 것**(그림/커버 자산의 다크 처리, 테마 부트스트랩 타이밍, `--text-faint` 재사용)에서 실제 결함이 나왔다 — 예상했던 "이질감"의 패턴 그대로다.

- `--graph-sel-parent-D`/`-child-D`: 비텍스트 3:1 기준으로 **8.26~9.67:1** — PASS.
- 검색 드롭다운(`.results .r span`, `--muted`=`--text-tertiary`) on `--surface-raised`: **4.74:1** — PASS(근소).

## §2. 시각 감사 (스크린샷 기반)

### 🔴 라이트 전용 자산이 새어 나오는 곳 — 흰 배경 그대로 노출

**A. 논문 페이지 "원문에서 가져온 그림" (`content/figures/*`)**
- 재현: 다크 전환 → `#/p/transformer` 또는 `#/p/resnet` → "구조 한눈에" 다음 섹션 "원문에서 가져온 그림"까지 스크롤.
- 실측: Transformer(Figure 1, 아키텍처 다이어그램)와 ResNet(Figure 2, residual block)의 그림 모두 **순백 배경 PDF 크롭이 프레임/보더/디밍 없이 카드 안에 그대로 삽입**돼 있다. 주변은 `#12161f`(거의 검정)인데 그림 영역만 `#ffffff`에 가까워 명도차가 극단적이다.
- **CSS 처리 전무**: `css/diagram.css`(자체 제작 다이어그램, `--dia-*` 토큰 사용)는 다크에서 완전히 정상 작동하지만, 이 "원문 그림"을 감싸는 마크업에는 다크 전용 규칙이 하나도 없다. `css/wiki.css`에서 `<img>`나 그림 컨테이너에 대한 `html[data-theme="dark"]` 규칙을 찾지 못했다.
- 논문마다 편차 있음: `#/p/gpt3`의 Figure(구성이 다른 차트)는 배경이 투명/짙은 PNG라 다크에서도 튀지 않았다 — **원본 이미지의 알파 채널 유무에 좌우되는 우연**이지 의도된 다크 처리가 아니다.
- 판단: 이건 "견딜 만한 수준"을 넘는다 — 페이지 전체가 짙은 톤으로 설계된 사이트에서 매 논문 상세 페이지마다 반복적으로 나타나는 가장 눈에 띄는 결함이다. 최소한 `filter: brightness/invert` 없이도 **흰 패널을 카드로 감싸고 얇은 밝은 테두리 + 약한 그림자를 주는 정도의 프레이밍**은 필요해 보인다(이미지 자체를 반전시키면 다이어그램 화살표 색 의미가 깨지므로 반전은 비추천).

**B. 책장 커버/호버 미리보기 카드 (`content/covers/*.webp`)**
- 재현: 다크 전환 → 홈 → 아무 책등 클릭(예: 컴퓨터 비전 레인의 ResNet) → 우하단에 뜨는 미리보기 카드.
- 실측: 카드 상단 이미지 영역이 **동일하게 순백 PDF 제목 페이지 크롭**이며, 카드 나머지 부분(칩, 제목, 저자, 버튼)은 전부 다크 토큰으로 잘 처리돼 있다 — 이미지 영역만 예외.
- `design/mock/cover-test.html` 목업으로 8개 샘플을 한 번에 봤을 때: 실제 커버 이미지가 있는 논문(Transformer, Gemini, GPT-4, Open X-Embodiment, 깊은 self-attention 문자 LM, vLLM 등)은 전부 흰 배경이 노출됐고, 커버 이미지가 없어 생성 폴백(두 글자 이니셜 + 분야색 배경, 예: 퍼셉트론→"FO" 녹색, SAE→"IN" 올리브)이 쓰인 카드만 다크와 조화로웠다. 즉 **실제 커버 보유 논문(대다수)일수록 오히려 다크에서 더 튄다**는 역설적 상황.
- 이 호버 카드는 책장 화면(홈)뿐 아니라 (코드상 `shelf:select` 이벤트로) 책 클릭 시 항상 뜨므로 **라이브러리 체험 전체에서 가장 자주 마주치는 다크 결함**이다.

**C. 검사했지만 문제를 못 찾은 것들**
- KaTeX 수식(`vendor/katex/katex.min.css`): Transformer 페이지의 attention 공식, positional encoding 공식 확인 — 다크에서 흰 배경 없이 텍스트 색만으로 잘 보인다(`--math-fg:var(--text-primary)`가 상속되는 것으로 보임). 별도 라이트 전용 값 노출 없음.
- 자체 제작 다이어그램(`css/diagram.css`, "구조 한눈에" 류 박스+화살표): Transformer/ResNet 양쪽에서 확인, `--dia-box-fill`/`--dia-box-border`/`--dia-arrow` 전부 다크 토큰을 정상 참조해 배경과 자연스럽게 어울림. 6종 중 이 "박스-화살표 플로우" 1종만 실제로 마주쳤고, 나머지 5종(다른 다이어그램 타입이 있다면)은 이번 감사에서 발견하지 못해 **확인 못 함**으로 남긴다.
- 계보 그래프(임베드 + 전체화면 뷰어): 레인 배경(`--graph-lane-bg:#161c28`), 노드(`--graph-node-fill:var(--surface)`), 선택 강조(부모/자식 색) 전부 다크에서 자연스러움. 단, §1의 미달 항목(축 라벨)과 §2-🟡(간선 대비)는 별도 기재.
- 그림자(`--shadow-1/2/3`): 다크 블록에서 `rgba(0,0,0,.4~.5)`로 재정의돼 있어(`tokens.css:420-422,490-492`) 라이트용 옅은 그림자를 그대로 쓰는 문제는 없음. 다만 배경 자체가 어두워 그림자가 "보이는지"는 카드 아래쪽을 확대해야 겨우 인지되는 수준 — 기능은 하지만 시각적으로 거의 무의미하다는 원 우려는 부분적으로 유효(육안상 있으나 마나).

### 🟡 계보 그래프 비강조 간선(edge)이 다크에서 거의 안 보임
- 선택자: `svg .edge` — `css/wiki.css:98`, `stroke:var(--graph-edge)` → `tokens.css:203` `--graph-edge:var(--border-strong)` → 다크 `--border-strong:var(--n-300)` = `#303b4e`.
- 실측: `#303b4e` vs `--surface`(`#12161f`) = **1.60:1**, vs `--graph-lane-bg`(`#161c28`) = **1.51:1**. WCAG 1.4.11(비텍스트 UI 요소/그래픽 객체 3:1) 기준에 크게 못 미친다. 강조 간선(`--graph-edge-hi:var(--accent)`)은 12.2:1로 매우 또렷해 대비 자체는 확실히 인지되지만, **강조되지 않은 나머지 대다수 간선(계보 관계의 본체)**은 전체화면 뷰어를 확대해야 겨우 보이는 수준이다.
- 재현: 전체화면 계보 그래프 열기 → 기초 학습 알고리즘 레인 근처 확대(`zoom` 400% 이상) → 노드 사이 연결선이 배경과 거의 구분 안 됨.
- 판단: "선택 시에만 강조되는 나머지는 옅게"라는 의도된 위계일 수 있으나, 1.6:1은 "옅음"이 아니라 "안 보임"에 가깝다. 라이트 테마 동일 토큰(`--border-strong:var(--n-300)`=`#ccd1dc` vs `--surface` `#fff`)은 1.35:1로 오히려 더 낮은데 그럼에도 라이트에서는 밝은 회색 선이 흰 배경 위에서 육안 식별이 되는 반면, 다크는 짙은 남색 선이 짙은 배경 위에 있어 체감 가독성이 더 나쁘다(휘도차는 둘 다 낮지만 다크 쪽이 절대 밝기까지 낮아 모니터 감마·눈부심 환경에 더 취약).

### 🟡 `--border-strong`의 다크 대비가 전반적으로 낮음
- 같은 `#303b4e` 토큰이 카드 테두리(`.card`, `.chip`, `.results`), input(`.gfv-search`), 구분선(`.shelf-row` 하단 2px 보더) 등 매우 넓게 쓰인다. 전부 1.6:1 내외.
- 스크린샷상으로는 "테두리가 있다는 걸 알아볼 수는 있는" 수준(장식적 구분선 정도로는 기능)이라 §2 A/B처럼 명백한 결함은 아니지만, **입력창·인터랙티브 요소의 경계**(예: `.gfv-search`, `.spine`)까지 같은 토큰을 쓰는 건 저시력 사용자에게는 "클릭 가능 영역이 어디까지인지 안 보이는" 문제로 이어질 수 있어 Medium으로 분류한다. 토큰 값 자체를 바꾸기보다 **인터랙티브 요소 경계용 토큰을 별도로 분리**하는 걸 권한다(현재는 장식용 구분선과 같은 값을 공유).

### 검사했지만 다크 고유의 문제를 못 찾은 화면
- 홈(책장 포함, 상단부터 "가로지르는 관심사"까지 전 구간 스크롤 확인), `#/f/llm`·`#/f/vision`(카드 그리드)·`#/f/foundations`·`#/f/privacy`(이름만 확인, 카드 나열 패턴은 llm과 동일한 컴포넌트라 별도 이상 없음으로 간주 — **개별 스크린샷은 못 찍음**), 검색 결과 드롭다운, `#/growing`(카드 46+개 중 상단 다수 확인), `#/course`(진행 배지), 좌측 내비(펼침/접힘), `AlphaFold 2`/`GPT-3` 상세 페이지.
- 각 화면에서 흰 배경 조각, 검은 텍스트, 밝은 테두리가 "새어나온" 사례는 §2-A/B 외에는 발견하지 못했다.

## §3. 테마 전환 자체

### 🔴 FOUC 구조적 위험 — 테마 부트스트랩이 `<head>` 밖에 있음
- `index.html` 12~17행에서 `css/tokens.css` 등 스타일시트를 로드하고, 45~59행에서 `content/fields.js` → `core.js` → … → `js/wiki/app.js` 순으로 스크립트를 로드한다. **테마를 읽고 `data-theme` 속성을 설정하는 코드는 `js/wiki/app.js` 5~12행**(파일의 맨 앞부분이긴 하지만, 파일 자체가 body 맨 끝, 다른 5개 스크립트 뒤에 로드됨)에 있다.
- 즉 브라우저가 `<head>`의 CSS를 파싱해 초기 스타일을 결정하는 시점에는 `html`에 `data-theme`이 없다. 이 상태에서 적용되는 규칙은 `tokens.css`의 base `:root`(라이트 값) 또는, OS가 다크면 `@media (prefers-color-scheme: dark)` 폴백(430행 이전 블록, `:root:not([data-theme="light"])`)이다.
- 실제 결함 시나리오: **OS가 다크로 설정된 사용자가 명시적으로 '라이트'를 선택해 저장한 경우**, 페이지 재방문 시 HTML 파싱 시점엔 `data-theme` 속성이 없으므로 `prefers-color-scheme: dark` 미디어쿼리가 매치되어 **일단 다크로 페인트되고**, 이후 `app.js`가 로드·실행되며 `localStorage`의 `'light'` 값을 읽어 `data-theme="light"`로 바꾸는 순간 **다크 → 라이트로 화면이 뒤집힌다.** 이는 과제에서 명시한 "`prefers-color-scheme`과 명시적 선택이 충돌하지 않는지"에 대한 실제 충돌 사례다 — 최종 상태는 맞지만 그 사이 전환 프레임이 사용자에게 노출된다.
- 반대로 다수 사용자(OS 라이트 + 저장된 선택 없음 → 기본값 `'dark'` 적용, `app.js:6`)는 base `:root`(라이트)로 먼저 페인트된 뒤 다크로 전환되는 라이트→다크 플래시를 겪는다.
- 재현/검증 방법: 네트워크를 느리게 제한(Chrome DevTools "Slow 3G" 등, 이 세션의 자동화 도구로는 스로틀링을 직접 재현하지 못해 **실제 깜빡임을 스크린샷으로는 확보하지 못함** — 코드 구조 분석에 근거한 판단이며, 로컬(빠른) 환경에서는 육안으로 인지하기 어려울 수 있음을 명시한다) 후 새로고침하며 관찰.
- 권고(참고용, 직접 수정은 하지 않음): 테마 결정 스크립트를 `<head>`의 첫 `<link rel="stylesheet">` 이전에 인라인 `<script>`로 옮기는 게 표준적인 해법.

### ✅ 새로고침 후 테마 유지
- `localStorage.getItem('wiki-theme')`(`app.js:6`)로 저장/복원. 실측: 다크로 전환 후 `location.reload()` 재현 시 다크 유지 확인(홈 화면 스크린샷 비교, "이어보기" 패널까지 정상 복원).

### ⚠️ OS 다크 + 첫 방문 → 다크로 시작하는지
- 결과적으로는 그렇다 — 하지만 **OS를 읽어서가 아니라 `app.js:6`의 기본값이 무조건 `'dark'`로 하드코딩**돼 있기 때문이다(`localStorage.getItem('wiki-theme')||'dark'`). **OS가 라이트인 사용자도 첫 방문엔 다크로 시작한다** — "OS 설정을 따른다"는 일반적 기대와는 다른, "기본값 자체가 다크"인 제품 결정이다. 버그는 아니지만 과제가 명시적으로 물은 질문이라 기록해 둔다. `prefers-color-scheme`은 JS 어디에서도 `matchMedia`로 조회되지 않는다(코드 전체에서 `matchMedia` 문자열 자체가 없음) — CSS의 미디어쿼리 폴백(§3 위 항목)만이 유일한 접점이고, 그마저도 FOUC의 원인일 뿐 최종 상태 결정에는 관여하지 않는다.
