# AI Wiki — 모션 예산 (MOTION.md)

이 문서는 사이트 전체의 모션을 규정한다. 짝 파일은 `design/mock/motion.html`
(제안 토큰을 실제로 재생해 본 목업, 크롬에서 스크린샷·JS로 검증 완료 — §8 참고)
이다. 상위 전제는 `design/LIBRARY-BRIEF.md` §2("읽는 데 방해되는 모션 금지",
스큐어모피즘·페이지 넘김·튀어나오기·시차스크롤 금지)이며, 이 문서는 그 금지를
어기지 않는 범위 안에서 **남은 모션 예산을 토큰화**한다.

원칙 한 줄: **모션은 이미 벌어진 상태 변화를 이해시키는 데만 쓴다. 무언가를
"멋있게 등장"시키는 데는 쓰지 않는다.** 이 원칙 하나로 아래 모든 결정이 갈린다.

## 1. 현재 진단 — 지금 흩어진 값

`css/wiki.css`, `css/diagram.css`를 전부 grep한 결과다(`css/diagram.css`에는

| 232 `details.graph-collapse>summary::before` | `.15s` (이징 미지정) | ❌ 리터럴 | `content` 삼각형 회전 느낌(실제로는 글리프 교체라 transition 무의미에 가까움) |

**숫자로 본 진단**:
- duration이 **6종류**로 흩어져 있다: 120ms(토큰), 140ms(리터럴), 150ms(리터럴),
  200ms(전용 토큰), 1400ms(리터럴), 그리고 트랜지션 없음(즉시).
- `tokens.css`에 `--duration-base:180ms`가 **정의만 되고 어디서도 쓰이지
  않는다** — 죽은 토큰. `.card`의 140ms가 사실상 그 자리를 대신하고 있었다.
- 이징은 **2계통**: 토큰화된 `cubic-bezier(.2,.7,.3,1)`(`--ease-standard`)과,
  `.14s`/`.15s`처럼 이징을 아예 안 써서 브라우저 기본값 `ease`가 암묵적으로
  걸리는 경우. `ease-in-out`(펄스 키프레임)까지 합치면 실질 3계통.
- `.card:hover`는 `transform`(위치) + `border-color`(색) + `box-shadow`(그림자,
  페인트 유발)를 **한 줄의 무조건 트랜지션**으로 묶어놨다 — 어떤 속성만
  애니메이트해야 하는지 규칙이 없었다는 뜻이고, 이게 §4의 성능 판단이
  필요한 이유다.
- `.graph-card-move:hover`처럼 트랜지션이 아예 없어 "버튼인데 눌러도 아무
  피드백이 없다"는 비일관성도 있다.

결론: 흩어진 6종 → 아래 §2에서 **4단계**로 접는다.

## 2. 토큰화

`css/tokens.css`에 추가할 토큰(실행자 참고용, 이 문서는 값만 정의하고
파일은 건드리지 않는다):

```css
--dur-micro:   120ms;   /* = 기존 --duration-fast. 이름을 새로 붙이진 않고 재사용해도 됨 */
--dur-state:   180ms;   /* 기존 --duration-base 재활용 — 지금까지 죽은 토큰이었던 걸 실제로 쓰이게 함 */
--dur-layout:  260ms;   /* 신규 — 여러 요소가 동시에 상태를 바꾸는 경우 전용 */
--dur-loading: 1400ms;  /* 기존 펄스 리터럴을 토큰화 (값은 그대로) */

--ease-standard: cubic-bezier(.2,.7,.3,1);  /* 기존 토큰, 그대로 */
--ease-decel:    cubic-bezier(0,0,.2,1);    /* 신규 — 여러 요소가 "정착"하는 레이아웃 전환 전용 */
--ease-loop:     ease-in-out;               /* 로딩 펄스 전용 — 기존 키프레임 값과 동일, 이름만 부여 */
```

`--graph-sel-duration`(200ms)/`--graph-sel-ease`는 **건드리지 않는다** —
GRAPH-INTERACTION.md §시-4에서 이미 근거를 세워 확정한 값이고, 이 문서의
새 스케일(180ms/260ms) 사이에 의도적으로 걸쳐 있는 예외임을 그 문서가
직접 설명했다. 이 문서의 역할은 그 예외를 존중하면서 **나머지 흩어진
값들**을 정리하는 것이다.

### 각 단계가 쓰이는 곳

| 토큰 | 값 | 쓰는 곳 | 대상 속성 | 왜 이 값인가 |
|---|---|---|---|---|
| `--dur-micro` | 120ms | 링크/버튼/칩 호버·포커스의 색·보더 변화, 복사 버튼 상태 전환 | `color`, `border-color`, `background-color` | 마우스가 지나갈 때마다 반복되는 "상시 인터랙션"이라 §8(DESIGN-SYSTEM 금지사항, 120~180ms 상한)의 하한값을 그대로 씀. 색만 바뀌므로 가장 짧아도 눈이 놓치지 않는다. |
| `--dur-state` | 180ms | 카드/책등 호버의 `transform`(리프트) + `box-shadow`, 디스클로저 삼각형 | `transform`, `box-shadow`, `opacity` | 위치·그림자가 같이 바뀌는 건 색 하나만 바뀌는 것보다 인지 부하가 크므로 한 단계 위(120→180ms). 지금까지 죽어있던 `--duration-base`를 여기 배정해 새 토큰을 늘리지 않았다. |
| `--dur-layout` | 260ms | 책장 필터 전환 시 다수 책등이 동시에 dim/복원 | `opacity`만 (§4) | 수십~수백 개 요소가 **동시에** 바뀌는 경우 180ms로는 "한꺼번에 깜빡"으로 보이고, 320ms 이상은 "필터가 느리다"는 인상을 준다. 요소 수가 많을수록 각 요소는 짧게 느껴지므로(동시성 착시) 오히려 개별 요소 기준으로는 단일 카드보다 살짝 길게 잡아야 "물결"이 아니라 "하나의 전환"으로 읽힌다. |
| `--dur-loading` | 1400ms(주기) | 지연 로딩 중 스켈레톤 펄스 | `opacity` | 값 자체는 기존 것을 존중(이미 "너무 빠르지도 느리지도 않다"는 합의가 있었다고 보고 바꿀 근거가 없음). 유일하게 **무한 반복**을 허용하는 예외 — §7에서 이유를 별도로 다룬다. |

이징은:
- `--ease-standard`: 모든 상태 피드백(micro, state)에 공통 사용. 그래프 선택
  강조도 이 값을 재사용 중이므로 사이트 전체에서 "무언가 바뀌었다"는
  느낌의 표준 곡선은 하나뿐이다.
- `--ease-decel`: `--dur-layout`(필터 재배치) 전용. 여러 요소가 동시에
  움직이는 게 아니라(§4에서 움직이지 않기로 결정) 여러 요소가 동시에
  "가라앉는"(dim) 것이므로, 감속 곡선이 "새 상태에 정착한다"는 느낌을 준다.
- `--ease-loop`(`ease-in-out`): 펄스 키프레임 전용. 왕복 운동이라 표준
  감속 곡선을 쓰면 한쪽 방향이 부자연스럽게 튄다.

## 3. 모션의 역할 규칙

**허용 원칙: 상태 변화(A→B, 실제로 값이 바뀌었다)를 이해시키는 모션만.
등장(존재하지 않던 게 나타남을 꾸미는 것)은 금지.**

### 허용

1. **인터랙티브 요소의 호버/포커스** — 링크·버튼·칩·책등·그래프 노드.
   이유: 마우스오버 전/후로 "클릭 가능 상태"라는 실제 상태가 바뀌었다.
2. **선택/토글의 시각적 전환** — 그래프 노드 선택, 필터 칩 on/off, 다크/라이트
   테마 전환(현재 즉시 전환 중이나 색 값만 바뀌므로 굳이 애니메이션 불필요 —
   테마는 순간적 "설정 변경"이지 관계를 이해시킬 필요가 없어 지금처럼
   즉시 전환 유지).
3. **로딩 중임을 알리는 펄스** — §7.
4. **버튼의 완료/실패 상태 전환**(`copy-link-btn.copy-done` 등) — 이미
   구현된 패턴, 상태가 실제로 바뀌었으므로 허용.
5. **필터로 인해 무관해진 항목을 낮은 불투명도로 표시** — §4. "이 항목은
   지금 조건에 안 맞다"는 실제 상태 변화.

### 금지

1. **페이지/화면 진입 시 요소가 순차적으로 나타나는 연출**(stagger fade-in,
   카드가 아래에서 올라오며 등장 등) — 나타난 이유가 "방금 상태가 바뀌어서"가
   아니라 "방금 로드돼서"이기 때문에 등장 연출이다. 금지.
2. **표지가 열리거나 튀어나오는 3D/플립 효과** — LIBRARY-BRIEF §2가 이미
   명시적으로 금지.
3. **스크롤에 반응하는 시차(parallax) 효과** — LIBRARY-BRIEF §2가 이미 금지.
4. **숫자 카운트업 애니메이션**(예: "446편" 이 0에서 굴러 올라가는 연출) —
   실제 상태 변화가 아니라 데이터 로드 완료를 과시하는 장식. 금지.
5. **호버 시 색이 요란하게 바뀌거나 확대(scale)되는 효과** — DESIGN-SYSTEM
   §8이 상시 인터랙션 120~180ms 상한을 이미 못박았고, `scale`은 책등처럼
   높이/두께가 데이터를 표현하는 요소에서 특히 위험(§4에서 "튀어나오는
   책"으로 오독될 소지).
6. **필터 전환 시 남은 항목이 빈칸을 메우려고 자리를 옮기는 리플로우
   애니메이션** — §4에서 별도로 다루는 성능·오독 문제.

## 4. 랜딩 책장의 모션

### 4.1 책등 호버/포커스 — **허용**

- 값: `transform: translateY(-6px)` + `box-shadow: var(--shadow-2)`,
  `--dur-state`(180ms) `--ease-standard`.
- 색·보더는 바꾸지 않는다(분야색은 항상 그대로 보여야 "이 동네" 신호가
  끊기지 않는다 — DESIGN-SYSTEM 원칙 2 재확인).
- 근거: 책등은 링크다(LIBRARY-BRIEF §4, "장식이 아니라 링크"). 호버/포커스
  피드백 없이는 클릭 가능함을 알 수 없으므로 이건 장식이 아니라 필수
  상태 신호다.

### 4.2 표지 카드 등장 — **애니메이션 없음, 즉시 교체**

- 책등을 클릭하면 표지 패널의 내용이 **즉시** 바뀐다. fade-in, slide-in,
  flip 전부 안 씀.
- 왜: (1) LIBRARY-BRIEF §2가 "책이 튀어나오는 효과"를 명시적으로 금지했고,
  fade-in조차 "표지가 짠 하고 나타난다"는 인상을 줄 수 있어 원칙과 방향이
  같은 잉크를 아낀다. (2) 이미 사이트의 다른 모든 화면 전환(홈→분야,
  분야→논문, `viewPaper()`의 `innerHTML` 교체)이 무모션 즉시 전환이다 —
  표지만 애니메이션을 넣으면 사이트 안에 두 가지 전환 문법이 생긴다.
  일관성이 화려함보다 우선.

### 4.3 필터 전환 재배치 — **재배치하지 않는다. 제자리 디밍만 허용**

이게 이 섹션에서 가장 중요한 결정이다.

- **결정**: 필터에 안 맞는 책등은 그리드/서가 상의 **위치를 그대로 유지한
  채** `opacity: var(--dim-opacity)`(그래프 선택의 `--graph-dim-opacity`인
  0.32를 그대로 재사용 — 새 값을 만들지 않는다)로 흐려진다. 필터에 맞는
  책등이 "빈칸을 메우러" 이동하는 리패킹(reflow)은 **하지 않는다.**
- **성능 판단(446개 동시 애니메이션)**: 이동(reflow)을 넣으려면 남은
  항목마다 새 grid 좌표를 계산해 `top`/`left`나 `grid-column`을 바꿔야
  하고, 이는 레이아웃을 트리거하는 속성이다. 446개 중 다수가 동시에
  레이아웃을 트리거하면 브라우저가 그 프레임에서 강제 리플로우를 반복
  계산(layout thrashing)하게 되어, 정확히 LIBRARY-BRIEF가 경계한 "첫
  렌더가 느려지면 실패"와 같은 성능 리스크를 필터 인터랙션에서 재현하게
  된다. 반면 `opacity`는 컴포지터 단계에서만 처리되는 속성이라 레이아웃을
  건드리지 않는다 — 446개가 동시에 바뀌어도 리플로우가 0회다.
- **대상 속성은 `opacity` 하나로 제한한다.** `transform`/`box-shadow`도
  동시에 걸지 않는다(호버와 달리 필터는 수백 개가 한 프레임에 동시
  발생하므로 속성을 더 얹을수록 페인트 비용이 선형으로 늘어난다 — 호버는
  항상 1개 요소에서만 발생하므로 §4.1처럼 여유롭게 두 속성을 써도 되지만,
  필터는 그렇지 않다).
- **오독 방지**: 위치를 유지하는 게 성능만의 이유는 아니다 — "어제 봤던
  그 책이 오늘도 같은 자리에 있다"는 예측 가능성은 UX-SPEC 4.3절이 계보
  그래프의 결정론적 레이아웃을 지킨 것과 같은 이유로 책장에도 적용된다.
  필터를 풀었을 때 책이 원래 자리로 "돌아오는" 게 아니라 "원래 거기
  있었다"고 느껴야 한다.
- 이 결정은 계보 그래프의 기존 선택 강조 패턴(`sel-dim`, 노드는 그대로
  두고 관련 없는 것만 흐리게)과 **동일한 어휘**를 재사용한 것이다 — 사이트
  안에 "관계없음을 표시하는 방법"이 두 가지 생기지 않는다.
- duration/easing: `--dur-layout`(260ms) `--ease-decel`. §2 표 참고.

### 4.4 표지 카드 등장 세부 — 위에서 다룸(§4.2). 이 섹션은 책등/필터만.

## 5. 페이지 전환(해시 라우팅)

**결정: 지금처럼 아무것도 하지 않는다.** `route()`가 `app.innerHTML`을
동기적으로 교체하는 현재 방식을 유지하고, 전환 애니메이션(크로스페이드
등)을 추가하지 않는다.

- 왜: (1) 홈은 446개 노드를 그려야 하는 화면이다. 전환 애니메이션을 넣으려면
  "이전 화면을 fade-out하는 동안 새 화면(446개 요소)을 이미 DOM에 올려놓고
  대기"시켜야 하는데, 이는 안 그래도 무거운 첫 렌더 예산(LIBRARY-BRIEF §4)을
  더 깎아먹는다. (2) 지금 사이트는 홈/분야/논문 어디를 가도 전환이 즉시라는
  점에서 이미 일관적이다 — 이 일관성 자체가 "빠르고 조용한 사이트"라는
  인상의 일부이고, 임의로 한 전환에만 모션을 넣으면 오히려 "왜 여기만
  다르지"라는 잡음이 생긴다. (3) 해시 변경은 사용자가 명시적으로 누른
  링크의 결과이므로 "어디서 왔는지" 방향성을 모션으로 알려줄 필요가 크지
  않다 — 브레드크럼(이미 있음)이 그 역할을 텍스트로 더 명확히 한다.
- 유일한 예외로 유지하는 것: 스크롤 위치 초기화(`window.scrollTo(0,0)`,
  이미 구현됨)는 모션이 아니라 순간 이동이므로 이 결정과 무관하게 그대로.

## 6. `prefers-reduced-motion`

"전부 0s"가 답이 아니라는 요구에 맞춰, **상태 변화를 이해시키던 정보가
reduced-motion에서 사라지지 않는지**를 항목별로 확인했다.

| 모션 | 평소 | reduced-motion에서 | 사라지는 정보와 대체 |
|---|---|---|---|
| 책등 호버 리프트(§4.1) | 180ms에 걸쳐 `translateY`+그림자 | `--dur-state:0` → 즉시 리프트된 최종 상태로 스냅 | 정보 손실 없음 — "호버 중"이라는 최종 상태(떠 있음+그림자)는 그대로 보인다. 없어지는 건 오직 "떠오르는 움직임"뿐이고 그건애초에 장식적 여지였다. |
| 미세 상태 피드백(§3-1,2,4) | 120ms 색 트랜지션 | `--dur-micro:0` → 즉시 새 색 | 정보 손실 없음. 색상 자체가 상태 신호라 전환 속도는 부가적. |
| 그래프 선택 강조 | 200ms 크로스페이드 | `--graph-sel-duration:0`(기존 tokens.css에 이미 정의) | GRAPH-INTERACTION.md가 이미 검증: 위치/크기를 안 쓰므로 즉시 전환해도 최종 상태 동일. |
| 필터 디밍(§4.3) | 260ms `opacity` 전환 | `--dur-layout:0` → 즉시 흐려짐/복원 | 정보 손실 없음 — "이 항목은 필터에 안 맞다"는 최종 상태(낮은 불투명도)가 그대로 유지된다. |
| 스켈레톤 펄스(§7) | 1.4s 무한 반복 `opacity` 왕복 | **애니메이션 자체를 끈다**(0s가 아니라 `animation:none`), 정적인 낮은 불투명도 + "불러오는 중…" 텍스트로 대체 | 이게 유일하게 "속도를 0으로"가 아니라 "반복 동작을 없앤다"로 처리해야 하는 항목이다 — 무한 반복 운동은 지속시간을 0으로 만드는 게 불가능(정의상 반복이 곧 모션)하므로, 대신 상태 자체는 텍스트(`불러오는 중…`)로 이미 이중 전달되고 있어(§7) 애니메이션이 빠져도 "로딩 중"이라는 정보가 사라지지 않는다. |

공통 구현 방식: `@media (prefers-reduced-motion: reduce){ :root{
--dur-micro:0ms; --dur-state:0ms; --dur-layout:0ms; } .skeleton.pulse{
animation:none; opacity:.75 } }` — `--dur-loading`은 값 자체를 0으로
만들지 않고 `animation`을 꺼서 처리한다(그래야 "펄스를 아주 빠르게
반복"이라는 어색한 중간 상태를 피할 수 있다). `--graph-sel-duration`은
이미 `tokens.css`에 별도로 처리돼 있으므로 이 문서에서 다시 정의하지
않는다.

## 7. 스켈레톤/로딩

논문 본문(`content/papers/<slug>.js`)만 지연 로딩 대상이고, 헤더(제목/메타/
브레드크럼)는 인덱스 데이터로 즉시 그려진다(`js/wiki/app.js` `viewPaper()`,
이미 그렇게 구현돼 있다 — UX-SPEC 3.3절이 이 즉시-헤더/스켈레톤-본문
분리를 개선 항목으로 이미 못박음).

원칙:
1. **펄스 애니메이션은 허용한다 — 단, "지금 기다리는 중"이라는 상태를
   표현할 때만.** DESIGN-SYSTEM §8이 120~180ms 상한의 유일한 예외로
   "로딩/스켈레톤처럼 정말 기다림을 표현할 때"를 이미 열어뒀다. 이 문서는
   그 예외를 스켈레톤 펄스 하나로 한정한다.
2. **펄스는 텍스트와 항상 같이 쓴다.** 지금처럼 `불러오는 중…` 문구를
   펄스와 병행 — 애니메이션만으로 "로딩 중"을 전달하지 않는다(모션을
   못 보는 사용자, §6 reduced-motion 대상 포함).
3. **446개 책등에는 스켈레톤이 없다.** 책장 데이터(`fields.js`,
   `graph.json`)는 이미 로컬에 있는 정적 산출물이라 홈 첫 렌더에 로딩
   상태 자체가 존재하지 않는다 — 스켈레톤을 넣을 대상이 없다. 표지 이미지
   (`/data/papers/<slug>/pages/p-01.png`)처럼 실제로 늦게 오는 리소스는
   `img loading="lazy"` + 배경색(`--surface-sunken`) 정적 플레이스홀더로
   충분하다 — **이미지 자리에도 펄스를 넣지 않는다**: 그림 633장·표지
   여러 장이 스크롤에 따라 동시에 로드되며 각자 펄스를 돌리면 화면
   여러 곳이 동시에 깜빡이는 잡음이 되고, 이는 "다음 콘텐츠가 아직
   없다"는 정보 이상의 장식이 된다. 정적 회색 박스만으로 "여기 이미지가
   온다"는 정보는 충분히 전달된다 — 애니메이션이 필요한 대기는 텍스트
   콘텐츠(본문 tldr)처럼 "얼마나 걸릴지 모르는" 로드에 한정한다.
4. **로딩 실패 시 펄스를 멈춘다.** (현재 `W.load(slug)`는 실패해도 무언가
   렌더한다는 전제이므로 별도 처리 불필요하지만, 향후 실패 상태 UI를
   추가한다면 펄스가 계속 도는 채로 남으면 안 된다는 원칙만 명시해 둔다.)

## 8. 검증

`design/mock/motion.html`에 위 토큰을 실제 값으로 넣어 4개 데모(필터
디밍/책등 호버·포커스/표지 즉시 교체/스켈레톤 펄스)를 만들고 크롬에서
확인했다:
- 필터 칩 클릭 → 24개 중 18개가 위치 변경 없이 `opacity`만 낮아짐(JS로
  `dimmed:18,total:24` 확인, DOM 순서·좌표 불변).
- reduced-motion 시뮬레이션 토글 → `--dur-micro`/`--dur-state`가 `0ms`로
  즉시 전환되는 것을 computed style로 확인.
- 책등 220개로 늘려도(성능 스트레스용) 필터 토글이 버벅이지 않음(오직
  `opacity` 트랜지션이라 레이아웃 비용이 없기 때문 — §4.3 판단의 근거).
